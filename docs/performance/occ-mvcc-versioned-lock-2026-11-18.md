# OccSTM 版本化锁 + 有界 MVCC：正确性基线与吞吐成本

记录日期：2026-11-18。此结果属于实验分支 `codex/occ-mvcc-versioned-lock-20261118`。
这份对照仅用于评估修复正确性问题的性能成本，**不能把旧实现当作等价正确的基线**。

## 正确性证据

原版 `main@7ceb0a73` 的 phase-gated 多变量交错，在写事务发布 A=1 后、
发布 B=1 前运行只读事务，实际接受了不一致的 `(1,0)`。
这个回归在旧版 [CI #44235607188](https://github.com/ZephyrVia/CaSTM/actions/runs/44235607188)
如预期失败。版本化锁的读前/读后验证已防止这一交错成功提交。

更新事务继续采用严格的读集验证，不放宽基于历史快照的写入冲突限制。
本文不将有限测试视为任何形式化 Opacity/Serializable 证明。

## 判断

版本化锁保留了**不同写 Stripe 并行提交**的能力，并没有像全局提交互斥锁那样
强行串行化全部写事务。额外的两次锁状态读取、读后 fence，以及遇到在途提交者的
保守重试，使得只读比重较高的负载出现一定成本。在本次 8T、高冲突、90R 场景中
成本较明显（TPS 约 -23.5%，p99 从 14.7μs 上升到 55.5μs）。

不应把旧版更快视为候选版性能失败：旧版已确认接受半提交快照，低于目标一致性
语义。当前没有证据支持为了吞吐删除读屏障或恢复旧协议。

如果后续需要继续优化读路径，可以研究为锁标记**待提交 WV**，并仅在
`pending_wv > RV`、历史版本完整且读前/后协议满足条件时允许读者避开在途
写入。但这需要新的协议证明、交错回归及实验，**不是当前实现已支持的能力**。

## 限制

- 三次短时样本不能证明小幅差异显著，也不是对长期 RSS、不同 CPU 或正式生产
  负载的通用预测。
- A/B 是修复版对**有已知正确性问题的旧版**的开销测量，不能用于两种等价正确
  算法的速度排名。
- TSan 仅覆盖既定 OccSTM/EBR 与 TierAlloc 部分场景；没有全仓库形式化正确性保证。
- 两版本均使用相同测试基准，可通过上面的 CI run 和 artifact 复核原始结果。
